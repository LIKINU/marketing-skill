# 反向榨 · R1/R2 落选与未落地项清算

> **什么叫「反向榨」**：R1（3 个 agent、31 条候选）与 R2（2 个 agent、20 条）共 51 条原始候选里，
> 有一部分**没有进入当轮 20 条**（当时判为「边际改进」或「成本大」），
> 或者进了清单但**执行时被跳过**。这一份把它们全部翻出来重判。
> **判据不是「当时为什么落选」，而是「现在回头看还值不值得做」** —— 因为前两轮已经把地基抬高了，
> 有些当时不起眼的条目现在变成了真缺口。

## A 类 · 被**两个及以上独立视角**重复指出的（最高优先，已在本轮做掉）

### A1. ⭐ `SKILL` 合约结构与 `composer` 输出**大面积漂移**，且**没有任何一关会发现**
- **来源**：R1 贝恩 agent 第 10 条 ＋ R3 运营 agent 第 10／11 条 —— **两个不同轮次、不同视角独立撞到**
- **实测坐实**（我自己 grep 过）：

| SKILL 合约里承诺的 | composer 是否生成 |
|---|---|
| `2.3 被低估的资产` | ❌ 不生成 |
| `2.4 節奏排期` | ❌ 不生成 |
| `7.3 追投與止損規則` | ❌ 不生成（编号还被「敏感性分析」占了） |

- **而为什么一直没人发现**：`selfcheck` 的 `SECTIONS` 是**手写的 9 个关键词**，
  与 `paradigm_data` 的 30+ 节**零对账**（实测在 selfcheck 里检索 `SKELETON_HEADS` 得到 0 处命中）。
- **本轮处理**：
  1. composer 补齐 `2.3 被低估的资产`／`2.4 节奏排期`／`7.4 追投与止损规则`／`8.9 复盘节点`；
  2. **治本**：`selfcheck` 新增【1b】关 —— 直接读 `paradigm_data.COMMON_HEADS` 逐节对账，
     缺节即报。**这条链终于闭环了**：composer 产出 → `build_paradigm` 校验声明 → `selfcheck` 校验交付稿。
  3. `SKILL.md` 的 `7.3 追投與止損規則` 改为 `7.4`，与骨架对齐。

### A2. ⭐ 行动清单**缺「谁验收／卡住时谁拍板」**
- **来源**：R1 贝恩 agent 第 4 条 ＋ R3 HR agent 第 1／18／19 条（**20 条中被三方共指**）
- **根因**（R3 才看清）：**骨架给的是 `【填】` 裸占位符，而检查要求「表＋若干列」** ——
  检查写得再严，骨架不给结构，必然空转。

## 反向榨的结论

1. **51 条原始候选 → 40 条入选 → 40 条执行完毕**，另有 **11 条落选**。
2. 落选的 11 条里，**2 条被后续轮次的不同视角重新撞到**（A1／A2）—— 说明「当时判为边际」有误判，
   **原因是当时地基还低**：议题树、单位经济这些「大件」没落地时，「每章回指假设」看起来是锦上添花。
3. **A 类的共同教训可以一句话概括**：
   > **检查写得再严，骨架不给结构，也必然空转。**
   这是 R1/R2 那条「文档承诺 ≠ 机械执行」的**下一个环节** ——
   R1 修的是「文档写了、脚本没查」；这一轮发现的是「**脚本查了、骨架没给位**」。
   两者合起来才是完整的：**文档承诺 → 脚本检查 → 骨架给位**，三环缺一都不成立。
4. **B 类 9 条建议单独开一轮做**，其中 B2（摸底模板与假设驱动相反）与 B4（案例卡洞察栏教错）最值得优先 ——
   它们动的是**上游**（怎么接案、知识库怎么教），比改下游产出更省力。
