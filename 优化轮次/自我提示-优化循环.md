# 自我提示 · 优化循环（我写给自己的作业指令）

> **这是什么**：一份**给执行 AI 自己的提示**。当用户说「继续优化这个 skill」而没给具体方向时，
> 直接按这份执行 —— 不用重新想方法、不用重新问要做几轮。
> **为什么要有它**：这套循环从 2026-09-17 跑出 R1→R2→R3 三轮、落地 60 条改进，
> 每一步的判据和踩过的坑都已经明确。不固化下来，下次会重新踩一遍。

---

## 一、启动前先答三个问题（不问用户，自己判）

1. **产出物归属**：这次是「交付给客户的」还是「改进 skill 的」？（前者要的是文件能交，后者要的是脚本/文档升级 —— 成本差一个量级）
2. **改哪一层**：`文档承诺 → 脚本检查 → 骨架给位` 三环里，断的是哪一环？
3. **这轮要不要派 agent**：只有在需要**独立上下文**（全新视角、读大量文件、无偏见审）时才派。
   重复格式内容生产**一律不派**。

## 二、循环的固定动作

```
① 派 N 个独立 agent（每个一个全新专业视角）
   → 每个 agent 的硬要求：≤12–20 条、每条带【文件+行号+原文片段】、
     不得凑数（凑不满就写「凑不满」）、不许泛泛而谈、**不许改任何文件**
② 收 25–35 条候选 → 去重排序取 20 条 → 写成 优化轮次/R{N}-20条.md
③ **交叉印证**：同一问题被 ≥2 个不相关视角撞到 → 标 ⭐，优先做
④ 按分组执行：真不一致/假绿 → 可绕过判据 → 缺关卡
⑤ 跑回归（见第四节）
⑥ 写「执行进度」回到同一个文件 → 提交 → 进下一轮
```

## 二·五、⛔ 派 agent 前必做的一件事（**否则同一个仓库被重读十几遍**）

> 用户 2026-09-17 指出：「**让你调 agent 修改的时候，每结束一次对话，再让你用 Agent 的时候，
> 又要重新再读一遍，一直重复。**」—— 这是真的：每个 agent 都是全新上下文。

**规矩**：派 agent 时，prompt 里必须写这两句 ——

```
## 先读这一份（**不要通读仓库**）
AGENT-BRIEF.md —— 仓库现状快照（约 3500 字）：是什么／多大／目录结构／脚本分工／
18 关自检／硬约定／**已知坑（8 条，每条都是踩过才知道的）**。
**只读这一份 ＋ 下面 1–2 个目标文件的「那一节」**；需要核对证据时用 grep 定位行号，
**不要通读整份文件**（`references/` 已 263 万字）。

## 你这轮只需打开
- `scripts/composer.py` 的 `build_skeleton` 与 `SCENE_SECTIONS`
- `scripts/selfcheck.py` 的【14】【15】关
（其余一律靠 AGENT-BRIEF.md 里的快照判断）
```

**这份快照由 `scripts/agent_brief.py` 生成，并挂在 `verify_all` 的幂等压测里** ——
改架构忘了更新它会被哈希漂移抓出来。**能生成的简报就不要手写。**

## 三、派 agent 时的 prompt 模板（照抄）

```
你是一位【具体职位，要真存在】，【一句带立场的话，体现他会被什么惹火】。
现在做一次「营销方案生成器的【具体角度】审计」。**只做研究和诊断，不要修改任何文件。**

## 背景
仓库根目录是一套「营销方案生成器」…
（规模、六档客户、知识由脚本机械注入、模型只填【填】、**本轮刚加了什么**）

关键文件（请实际打开读）：【列 5–7 个，含 composer.py 与 selfcheck.py】

## 你只审这个角度：【一句话界定范围，别让他跑题】
1. 【7–9 个具体追问，每个都要指向可查的地方】

## 输出要求（严格）
返回**最多 N 条**，按投入产出比降序。每条四字段：
### N. 一句话标题
- 现状证据：文件 + 章节名或行号 + 原文片段（≤40 字）。不许写「文中多处」。
- 差距：以【该行业的合格线】衡量，差在哪（一句话）。
- 具体改法：改哪个文件、加什么字段/检查项。脚本改动写到「加什么函数、判什么、输出什么」。
```

## 三·五、⛔ 改完先跑 impact（**不要再靠"记住跑哪几条"**）

```bash
python scripts/impact.py              # 读 git status → 算出必须重跑 + 必须同步改
python scripts/impact.py --verify     # 直接跑一遍
```

**为什么**：用户问「**修了一个就应该把所有影响都预计好，为什么要多次质检？**」——
这直觉是对的。编译器能做到「改签名→列全部调用点」，是因为**依赖边写在类型里**；
本仓库原先的边散在文字里（SKILL 的一句话、维护纪律表），所以只能靠人记 → 人必漏 → 漏了再跑一轮兜。
`impact.py` 就是把那些边**从文字搬进数据**。

**每碰到一条没建模的边，就补进 `impact.py` 的 RULES。补一条，下次少一次盲目重跑。**

## 四、回归必须跑全（一条都不能省）

```bash
python scripts/smoke_test.py                 # 12 项冒烟（含标杆稿必须通过）
python scripts/kb_audit.py                   # L1–L7 断链必须全 0
python scripts/promise_check.py              # 文档承诺 ↔ 实际执行
python scripts/optimize_scan.py              # 每轮 ≤10 条可优化点
python scripts/verify_all.py -n 50           # 全链路 + 50 遍幂等（读起来 6 分钟）
```
> ⛔ **`verify_all` 运行期间绝对不要改仓库文件** —— 它会把「运行中被改动」如实报成哈希漂移，
> 而你会以为脚本非幂等。已经踩过一次。

## 五、六条已经被血换来的判据（新加东西前必须过一遍）

1. **新硬关必须先问「这条要求对最轻的那档也成立吗」** —— 已连续四次误伤速览类快案。
   完整版才强制的，走 `_hard_if_full()`。
2. **检查器要能区分「代码在找这个字符串」与「代码要访问这个路径」** —— 否则会把自己的
   正则、占位符词表、索引串当成真问题（「提到 ≠ 读取」「引用 ≠ 消费」）。
3. **拿真稿调参，不要拿想象调参** —— 「为什么这么做」的判据初版误伤了机制句，
   补了条件推演/对照取舍/推理链三类句式才准。
4. **`except: pass` 一律不许** —— 最危险的一处：`verify_all` 哈希读不到文件就跳过，
   于是「文件怎么变都测不出漂移」，而报告照样印「零漂移」。
5. **脚本查了 ≠ 骨架给了位** —— 检查要求「表＋若干列」而骨架只给 `【填】`，检查必然空转。
   三环必须齐：**文档承诺 → 脚本检查 → 骨架给位**。
6. **口径只能在同层比较** —— 「月/年混用」检查做成了整份文档范围，把分列清楚的标杆稿误判了；
   改成按**表块**判断才对。

## 六、收尾（每轮固定）

- 把「执行进度」写回当轮文件（含未做项与理由）
- `git commit`，**不要 `git push`**（用户在内地，推送不通是预期；说一句「已提交待推送」即停手）
- 回复用户时：先说结论、再给证据，**不要罗列过程**
